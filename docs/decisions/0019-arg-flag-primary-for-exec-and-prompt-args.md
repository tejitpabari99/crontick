# 0019: `--arg` is the primary way to pass arguments to `--exec`/`--prompt`

- Status: Accepted
- Date: 2026-07-27

## Context

ADR 0018 made `--exec <command> -- <args...>` the CLI's answer to passing arguments
verbatim, reusing the `--` convention already used by prompt-mode jobs. In practice,
`--` is not a crontick-controlled behavior once it crosses an npm-generated Windows
shim: `npm install -g crontick` produces `crontick.ps1`, `crontick.cmd`, and a POSIX
shell script, and the wrapper actually invoked depends on which shell resolves the
bare `crontick` name.

Testing against all three real Windows entry points (`crontick.ps1`, `crontick.cmd`,
`npx crontick`) surfaced two independent, verified shim defects that `--` alone cannot
work around:

- PowerShell's own parameter binding drops a literal `--` token before the `.ps1`
  script ever receives argv, so `--exec ... -- ...` silently loses every argument
  after `--` under a bare `crontick` in PowerShell.
- `cmd.exe`'s argument handling strips embedded double quotes before the `.cmd` shim
  sees them, so an argument containing an embedded `"` arrives corrupted even when
  `--` itself survives.

Neither defect is a crontick bug -- both live entirely in the shim/shell layer -- but
documenting `--` as *the* way to pass exec/prompt arguments left every Windows user of
the generated global shims with a silent-corruption trap on a first release with a
stated goal of no undocumented gaps.

## Decision

A new repeatable `--arg <value>` flag (`src/cli/index.ts`) is the primary, documented,
always-correct way to pass arguments to `--exec` and `--prompt`/`--prompt-file` jobs.
Each `--arg <value>` occurrence appends one array element to the action's `args`;
repeating it any number of times builds the full argument list
(`crontick new job --exec node --arg -e --arg "process.stdout.write(1)"`). `--arg`
round-trips spaces, embedded double quotes, leading dashes, and values that are
spelled like crontick's own flags (`-v`, `--json`, ...), verified against all three
real entry points (`crontick.ps1`, `crontick.cmd`, `npx crontick`) -- see the matrix
below.

`resolveActionArgs()` (`src/job-input.ts`) resolves the final argument list from
either `--arg` (`input.args`) or the `--` convention (`input.rawArgs`/`engineArgs`),
and rejects combining both in the same command
(`"Cannot combine --arg with -- positional arguments in the same command..."`) since
there is no sensible way to merge two argument-list sources for one action.

`--` continues to work and is kept as a convenience for the common case (a POSIX
shell, or `crontick.cmd`/`npx` invoked directly) where its brevity is nice and its
known shim caveats do not apply. It is not removed and not deprecated; it is
demoted from "the" mechanism (ADR 0018) to "a" mechanism, with `--arg` as the one
that is always correct regardless of which shim resolved the command.

A new `assertNoCrontickFlagCollision()` check rejects (rather than silently
absorbing) a crontick long-flag spelling placed after `--`, so a user who mistypes
flag order gets an explicit error pointing at `--arg` instead of a job silently
created with the flag's text as a literal argument.

**Verified behavior matrix** (real shims, not simulated):

| Form | `crontick.ps1` | `crontick.cmd` | `npx crontick` |
|---|---|---|---|
| `--arg <value>`, incl. spaces / leading dash / flag-like value | works | works | works |
| `--arg <value>` with embedded double quotes | works | fails -- cmd.exe strips embedded quotes | works |
| `--` passthrough | fails -- the PowerShell shim drops the literal `--` | works without quotes | works |
| crontick flag placed after `--` | rejected | rejected | rejected |

Recommendation for Windows users who need embedded quotes and are stuck with the
`.cmd` shim: use PowerShell or `npx` instead of `.cmd`, or prefer `--arg` (which
works everywhere) over `--` in the first place.

## Alternatives considered

**Fix the shim generation itself (ship a corrected `.ps1`/`.cmd`).** Rejected: the
shims are generated by npm at install time from `package.json#bin`, not shipped by
crontick; crontick has no supported way to override npm's shim generation, and the
underlying PowerShell parameter-binding behavior (dropping `--`) is a documented
PowerShell behavior for any `.ps1` script, not an npm defect to patch around.

**Deprecate or remove `--`.** Rejected: `--` still works correctly on POSIX shells,
`crontick.cmd`, and `npx`, and it is a familiar convention; removing it would break
existing scripts for no benefit to the platforms where it already works.

**Tell Windows users to always invoke `crontick.cmd`/`npx crontick` explicitly and
leave `--` as the only argument mechanism.** Rejected: this still leaves the
embedded-double-quotes gap unaddressed under `.cmd`, and asks every Windows user to
remember a shim-selection rule instead of giving them one flag that is correct
everywhere.

## Consequences

**Easier:**

- One flag (`--arg`) is correct on every real invocation path (`crontick.ps1`,
  `crontick.cmd`, `npx crontick`, and every POSIX shell), so documentation and
  examples no longer need a platform-conditional recommendation for the common case.
- A crontick flag accidentally placed after `--` now fails loudly
  (`assertNoCrontickFlagCollision`) instead of silently becoming a literal job
  argument.

**Harder:**

- Users must learn a second argument-passing flag (`--arg`) in addition to `--`,
  and repeatable-flag syntax (`--arg a --arg b`) is more verbose than a single `--`
  run for a short argument list.
- `--arg <value>` where `<value>` is spelled like a crontick global flag
  (`-v`, `--json`, ...) requires a pre-parse rewrite
  (`rewriteArgValuesCollidingWithGlobalFlags`) to keep Commander's global flag scan
  from swallowing it; this is an implementation detail users do not see, but it is
  a permanent piece of parsing complexity this decision commits to maintaining.

**Impossible:**

- A single argument-passing flag that is simultaneously as terse as `--` and immune
  to every Windows shim defect discovered; `--arg`'s repeatable-flag form is the
  price of that immunity.

## Revisit when

- npm ships a fix for the PowerShell-shim `--`-dropping behavior, or crontick moves
  to a shim format it fully controls (e.g. a compiled binary) -- at that point `--`
  could be safely promoted back to primary, or `--arg` could be dropped if it is judged
  no longer to carry its weight.
