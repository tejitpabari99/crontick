## Must-fix
- [Bug Hunter] `src/daemon/store.ts` `hasCompletedClaudeSession` (~line 603) required `status IN ('success','failed')` on the run row that captured the session. `runner.ts`'s `execute()` sets the run's status to `'running'` at the start and only calls `finalizeRun` after the whole retry loop (~runner.ts:397), reusing the SAME run row across attempts. With `action.reuseSession: true` and `job.retry.max >= 1`, attempt 1 fails but still parses a Claude result line (captures the session, `markCompletedClaudeSession` ~runner.ts:770), leaving the row at `status: 'running'`. Attempt 2's resume preflight (~runner.ts:508-514) then calls `hasCompletedClaudeSession(job.id, sessionId)` → false solely because the row's status is still `'running'` → aborts with `SESSION_NOT_FOUND`, breaking the retry loop after a single attempt instead of resuming into the session attempt 1 captured.
- [Architect] `src/daemon/store.ts` `prepareImportedJob` (~lines 287-301) branched on `engine?.type !== 'claude'` — a literal engine-name check in core daemon code, violating design-principles.md #1 (core never inspects `engine.type` beyond a registry lookup). `runner.ts` (~508-519) already gates the identical concern generically via `adapter.resumeTranscriptPath(...) !== undefined`, so the same engine (Claude) got two different, potentially divergent routes to the same "does this engine need transcript-backed resume provenance" question.

## Notes (non-blocking)

## Resolution

Both must-fix findings and the hardening note were fixed in one commit (see below).

- `src/daemon/store.ts`: `hasCompletedClaudeSession` now keys eligibility purely off `claude_result_completed = 1` (dropped the `status IN (...)` clause). `prepareImportedJob` now routes through `getEngineAdapter(engine.type).resumeTranscriptPath(...) !== undefined` (imported from `../engines/registry.js`) instead of `engine?.type !== 'claude'`, matching `runner.ts`'s own resume-provenance gate.
- `src/engines/claude-transcript.ts`: added `isUnsafeSessionId()` and sanitization inside `resolveTranscriptPath()` — an unsafe sessionId (path separator, `..`, or NUL) is substituted with a marker filename that can never exist on disk, so it fails the existing `transcriptExists` preflight closed instead of ever being joined unsanitized into a real path.

Tests added (`tests/unit/claude-adapter.test.ts`):
- `resumes across a retry within the same run when reuseSession captures a session mid-loop` — reuseSession: true, retry.max: 1, attempt 1 fails (is_error: true) but captures a session, attempt 2 resumes with `--resume <sessionId>`; asserts 2 real spawns, the exact resumed session id, and a final `status: 'success'`. Confirmed failing before the fix (`attempts` stuck at 1, matching the reported bug exactly) and passing after.
- `never lets a path-traversal sessionId escape the transcript directory` — unit test on `isUnsafeSessionId`/`resolveTranscriptPath`.
- `fails closed before spawn for a path-traversal sessionId, even when marked completed` — integration test against the real (unstubbed) `transcriptFileExists`, proving no traversal-crafted path is ever treated as found.
